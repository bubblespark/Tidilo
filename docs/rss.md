# RSS and Atom Subscriptions

Settings > Data Management is ordered Summary, RSS, Clear Image Cache. RSS (`settings_rss`) manages RSS 2, Atom, and RDF subscriptions. All subscription state, receipts, article content, and AI output remain on the device. Feed acquisition requests the publisher's XML and article HTML through shared manual/RSS preparation; it does not send bookmark content to an AI service.

## Settings and acquisition

- Daily fetch time defaults to **00:00 local time**. The Material 3 time picker changes the shared schedule. Execution is approximate and can be delayed by Android power management.
- **Fetch only over Wi-Fi** appears immediately below the time control and defaults ON. When ON, scheduled acquisition and the ordinary Settings **Fetch now** action, including their related image/icon requests, require validated Wi-Fi transport. The sole exception is **Fetch now in the post-registration initial-fetch dialog**: explicit confirmation permits mobile data for that one operation and its related requests without changing the setting. OFF permits other validated Internet networks.
- Requests bind to the selected network. Losing Wi-Fi cannot transfer a request to cellular. Waiting work remains pending without creating a separate job for every missed day. The time uses an outlined input-like control. Beside it, a small red Cannot fetch: Wi-Fi is not connected. warning appears only after connectivity has been checked and Wi-Fi-only is ON without validated Wi-Fi. No waiting label is shown; an unknown initial connection state does not show a warning.
- WorkManager owns unique daily periodic work and unique manual work. Startup, preference edits, clock/timezone changes, and successful execution correct scheduling. Updating Wi-Fi policy also updates a pending manual request's constraints without losing its original request time.
- ETag and Last-Modified validators support 304 responses. Individual feed failures do not prevent other feeds from importing. Eligible transient article failures retry with WorkManager backoff; feeds already successful for that request are skipped only when no incomplete acquisition remains.
- Each response is limited to 2 MB and a 30-second monotonic deadline, with individual connect/read timeouts of at most 10 seconds and at most six connection attempts including redirects. Direct enrichment uses windows of 20 entries and at most four simultaneous requests. These bounds do not impose an article-count ingestion limit.
- Feed cards show the fetched title and a single-line URL, followed by a compact horizontal summary such as Direct / Max30 or AI Analyze / Unlimited. Edit and Delete sit at the bottom left; an accessible Enabled On/Off switch sits at the bottom right. Feed cards use 16dp padding and 6dp vertical spacing while other Settings cards keep their existing spacing. Errors remain visible. Attempt/success timestamps are internal only. A successful acquisition clears the previous error. Disabled feeds are excluded from scheduled and manual acquisition while saved articles and pending AI tasks remain. Fetch now provides an explicit refresh/retry. Registration validates a real supported XML document over any available validated Internet connection, regardless of Wi-Fi-only. It discovers the feed title and saves the subscription without fetching article HTML/images/icons, queuing AI, recording consumed receipts/acquisition success/validators, or deleting articles. Missing connectivity or invalid XML does not complete registration.

- After successful registration, **Later** retains the subscription and waits for the next normal scheduled cycle. Dismissing the timing dialog has the same effect. **Fetch now** schedules only this subscription. A red mobile-data notice appears when Wi-Fi-only is ON without validated Wi-Fi; explicit confirmation permits only that persisted operation and its related requests. Wi-Fi-only preferences and ordinary Settings Fetch now restrictions remain unchanged. A connection change that newly requires the override must first display the notice before permission is granted.
- An actual XML request or feed parsing failure immediately switches the affected subscription's **Enabled** OFF. Its card persistently explains that XML could not be fetched and the feed was automatically disabled. Existing bookmarks, tasks, receipts, and caches remain. Other feeds continue. Manually re-enable the feed to make it eligible for the next scheduled/explicit fetch; the explanation clears after successful XML acquisition. No validated connection, a required-Wi-Fi wait, cancellation, or worker interruption is a wait rather than an automatic-disable failure. Article/image failures never disable the entire feed.

## Parsing and images

`RssFeedParser` uses the existing Jsoup XML parser. It handles namespaces, CDATA/escaped HTML, RSS GUIDs, Atom IDs and HTML alternate links, relative URLs, `xml:base`, and publication dates. Only HTTP(S) article/image URLs without embedded credentials are accepted. URL normalization preserves query strings and removes fragments. Missing titles fall back to the URL/host; missing publication dates use first-seen time for selection and retention. Atom updated time is not treated as publication time.

XML provides article URLs, publication dates, subscription provenance, and consumed-item identities. Article preparation uses the same HTML parser and metadata rules as manual import: nonblank OG title then HTML title then host; nonblank OG Description then standard Description then empty; OG site name then host; Readability body then cleaned Jsoup body, truncated to 800 characters with newlines replaced by spaces. Explicit manual title overrides remain user input. XML excerpts do not become prepared article content.

Direct saves the HTML Description, including an empty Description when absent, without AI classification/keywords or AICore calls. AI Analyze uses genuine extracted HTML content; if both body and Description are empty, acquisition remains an error. HTTP/fetch/parse failures produce durable article errors, never silent XML-only bookmarks or URL-only inference. Direct retries stay Direct. Transient article failures receive bounded retries; nonretryable HTTP failures remain available for explicit retry. Feed 304 responses or entries disappearing from newer XML do not discard persisted article retries.

The already acquired HTML supplies OG image URLs and the complete icon candidate list, including a known-empty discovery result. Both manual and RSS imports avoid another article request merely to discover icons. Existing separate root-page discovery, candidate priorities, cache identities, eviction recovery, and generation-safe publication remain. RSS HTML, redirects, related images/icons, and root-page discovery use a request-scoped network transport; manual imports retain ordinary connectivity behavior. Compatible requests coalesce, while differently authorized network work cannot borrow another caller's mobile permission. Cached files remain shared. Optional image/icon failure does not invalidate successfully prepared article content.

Explicit article retries use the same feed enablement/revision checks for related requests. A missing permitted network is recorded as a wait on the affected task without consuming an acquisition attempt, disabling its feed, or failing unrelated foreground AI work.

## Modes, queue, and inference

New feeds default to **Direct**, with a retention count of **30**.

- **Direct** saves every valid unseen entry supplied by the fetched feed. It bypasses Ready tasks and does not invoke AICore. It has no ingestion-count cap.
- **AI Analyze** keeps the newest **five unstarted tasks per feed**, counting READY and WAITING_AI together. Existing unstarted tasks and new entries compete by publication time, then first-seen time and stable URL/ID ties. PROCESSING_AI and ERROR are outside that cap. Dropped older entries are recorded as consumed.
- Import displays Ready, Ready - RSS, and Error separately. Each Ready section has independent expansion and five-item preview/More controls, with the existing swipe and Undo actions. RSS errors retain feed provenance.
- The foreground import worker selects waiting manual tasks before RSS tasks at every iteration. An already active inference finishes normally. Scheduled workers only acquire and persist data; they never invoke AICore. Foreground auto-run settings continue to govern automatic promotion and inference.
- Inference starts only after an atomic SQL claim checks the task and its subscription. Removed or no-longer-AI subscriptions move invalid retry waiters back to Error, avoiding a repeated selection loop. Cancellation, quota rollback, and Undo reconcile the unstarted-task cap. AI success and fallback preserve RSS ownership, publication date, and first-seen time.
- Maximum AI queue is shown in small text and equals five times the number of enabled AI feeds. A warning above 20 possible tasks is a heuristic, not an SDK quota or remaining-capacity estimate. Running tasks, errors, retries, manual imports, and debug usage are separate.

## Persistence, duplicates, and lifecycle

Room schema **11** adds `import_notifications` through `MIGRATION_10_11`, along with `clearRssFeedId` queries on `bookmarks` and `import_tasks` to support reverse RSS promotion and duplicate notifications (Issue #97). Room schema **10** adds explicit HTML preparation, intended import mode, entry identity, durable article retry fields, and feed-scoped acquisition checkpoints/mobile permission through `MIGRATION_9_10`. Existing RSS XML snippets remain unprepared even when nonblank; existing manual prepared snippets keep their behavior. Schema **9** adds an enabled flag through `MIGRATION_8_9` (existing subscriptions remain enabled and retain their configured counts). The original RSS schema, through `MIGRATION_7_8`, adds `rss_feeds`, `rss_seen_items`, and `rss_image_cleanup`. Nullable `rssFeedId` and `rssPublishedAt` fields on bookmarks, trash, and import tasks preserve existing manual rows and source identity. Indexed `ogImageKey` fields are backfilled from existing image URLs for targeted reference checks. Search-derived columns and normalized tag occurrences remain maintained by the existing DAO transactions.

Receipts use feed identity plus GUID/Atom ID, with normalized URL fallback and a URL lookup. Receipt insertion, duplicate checks, content/queue changes, and retention selection commit transactionally. A failed transaction does not consume an entry. RSS ingestion skips URLs already present in the library, trash, or import queue, preserving the existing record. Retention deletion and queue replacement do not cause receipt replay. Manually importing a URL already acquired by RSS promotes the item according to Issue #97:
- **Case A (Library RSS, AI Complete)**: Clears `rssFeedId` to promote it to a normal user bookmark without re-analyzing, and records an `INFO` notification with tap navigation to detail.
- **Case B (Library RSS, AI Unanalyzed/Skipped)**: Enqueues into normal `Ready` (`rssFeedId = null`) for AI tagging while preserving the original bookmark identity, user note, and creation timestamp upon save, recording an `INFO` notification.
- **Case C (`Ready - RSS` Task in Queue)**: Clears `rssFeedId` directly on the task entity to move it to the top-level `Ready` queue without re-fetching, and records an `INFO` notification.
- Retention of `rss_seen_items` ensures promoted articles are never re-acquired by subsequent RSS feed syncs.

Changing mode applies to future acquisition. Switching AI to Direct offers saving or discarding existing unstarted tasks; active work and errors are separate. Editing the URL registers a validated replacement before removing the previous subscription. Deleting a subscription stops future acquisition and removes unstarted tasks while preserving saved RSS articles, error records, and source identity. Revision checks reject stale fetch results after edits or deletion; saved articles never become manual merely because their subscription was removed.

When saving unstarted tasks during AI-to-Direct conversion, already HTML-prepared tasks save directly without another request. Unprepared legacy/acquisition tasks retain Direct intent and wait for policy-compliant acquisition. Conversion does not trigger count deletion. Explicit promotion or cancellation during acquisition is rechecked at completion rather than overwritten by the earlier task snapshot.

## Retention and cache cleanup

Unlimited disables automatic count deletion. A count from **10 to 500** keeps that many active RSS-owned articles for each feed. It is independent of acquisition and queue limits and is not an age measured in days. Retention runs at scheduled/explicit acquisition checkpoints, including successful XML 304 cycles. Registration, reducing a setting, pending-task conversion, and foreground AI/fallback saves do not independently select articles for deletion. Saved RSS counts can temporarily exceed the configured count until the next eligible acquisition cycle; disabled feeds can remain above the limit until re-enabled. The oldest publication date, with first-seen fallback, is removed first. Automatic deletion is permanent and bypasses Trash; manual bookmarks and running tasks are protected.

Trash mappings and targeted AI-review edits preserve source fields. A future restore through the bookmark-save path is subject to the source feed's limit at the next acquisition/cleanup cycle; issue #91 does not add a new trash-restoration interface.

Deletion records a durable image-cleanup outbox after selecting excess bookmarks. Cleanup checks indexed canonical image identities across active bookmarks, trash, and unfinished tasks. Shared relative/absolute image aliases stay protected. Only unreferenced exact cache files are deleted; domain icons are preserved. A domain-latest image is removed only when there are no other domain references and its bytes match the deleted exact image. Per-image epochs reject publication by older in-flight loads/downloads and invalidate memory entries. Failed deletions remain queued for a later cleanup pass.

## Browsing

Library's Newest First and Domain modes show manual bookmarks only. RSS mode shows RSS-owned bookmarks, including those from deleted subscriptions, using the existing newest-first list/grid presentation. Source changes clear a selected domain and reset the relevant scroll position. Search and Tag Selection include both sources with the existing NSFW rules. Summary counts include both sources and exclude trash from the active total.

## Verification boundaries

JVM fixtures cover formats, metadata, HTTP validators/failure handling, stable selection, scheduling/DST, source mapping, manual queue priority, empty RSS bodies, first-seen fallback, and subscription-removal races. Android tests exercise real Room upgrade paths, source queries, receipt rollback/replay, concurrent ingestion, retention, task claims, Undo, canonical image references, Wi-Fi constraints, in-flight image deletion, and labeled Settings controls. Network and AI work in automated tests use fixtures or fakes. Actual AICore inference and real mobile/Wi-Fi handover require a physical supported device; the emulator does not provide AICore.

The feed editor groups Direct/AI Analyze under Import Mode and Unlimited/retained count under Max saved items. New feeds default to30; editing existing subscriptions preserves their settings. Fetch now uses a filled Material button.

## Acquisition reliability and HTTP policy

Requests prefer validated Wi-Fi even when Wi-Fi-only is OFF; another validated network is allowed only as fallback. Actual feed-XML acquisition/validation failures disable the feed immediately. Transient article errors retain up to five failed attempts durably, then require explicit retry. Worker execution uses bounded slices and durable item checkpoints; time-slice yields and connectivity waits do not consume the publisher-error retry budget. Incomplete operations resume through WorkManager, with startup reconciliation as a fallback. Missing Wi-Fi remains a connectivity wait and does not itself terminate the request. Clock/timezone receiver failures are logged and always finish the asynchronous receiver.

Arbitrary user-provided HTTP feeds remain supported intentionally. The manifest therefore permits cleartext HTTP throughout the app, including page and image connections. HTTP traffic has no transport encryption or integrity protection: a network observer can read it, and an on-path attacker can modify XML, metadata, article links, images, or content used in an on-device prompt. HTTPS should be preferred when the publisher supports it. A fixed-domain network-security allowlist cannot cover arbitrary hosts added at runtime. This policy does not add cloud AI or upload bookmark content.

Atom body selection distinguishes the Atom namespace from Media RSS regardless of prefix spelling. Missing, blank, or malformed AI summaries retain a nonblank prepared HTML Description before falling back to the title. Manual task priority and deterministic undated-entry URL/ID tie-breaking are unchanged.

## Re-registering the same feed

A normalized feed URL remains unique. Re-registration reuses the original subscription ID and consumed-item receipts; it does not create duplicate feeds or detach old articles from retention. While unsubscribed, saved articles remain. Once re-registered, both existing and newly acquired articles are subject to the newly selected retention limit.

If active RSS bookmarks already exist for that feed, registration first asks for confirmation showing their count. A count limit warns that oldest excess articles are permanently removed without Trash, when a scheduled or explicit fetch performs count cleanup; registration itself does not delete articles. Unlimited explains that existing articles remain without count deletion. Cancel leaves the subscription and articles unchanged. The repository checks consent before network validation and rechecks ID, revision, and count transactionally before reactivating the subscription. A changed count requires another confirmation. Only active RSS-owned bookmarks for that feed are counted; manual records and Trash are outside this retention scope.

The deprecated network enumeration is intentionally retained with a local suppression and explanatory comment: non-default validated Wi-Fi routes must be discoverable for explicit connection binding. Cached image ownership checks compare file lengths before allocating bytes for an equality comparison.
